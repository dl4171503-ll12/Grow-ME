# 追问闸门（grow-me Phase 0 详解）

> 本文件只在 Phase 0 需要展开时读。核心机制参考 grill-me（Matt Pocock 的 grilling / matt-riley 的
> agent-skills 版本）的"设计树 + 前沿轮次"，并针对代码任务做了裁剪：**事实归自己，决策归用户**。

## 目标

开工前把设计树上的每个分支都解决掉，做到"不需要猜"。追问本身不是目的 —— 少一轮返工就是省一笔积分。

## 前沿轮次算法

```
1. 列出所有未定决策，标注每个决策依赖哪些其他决策
2. frontier = { d | d 的所有前置决策已定 }
3. 若 frontier 为空 → 进入"合成"（见下）
4. 从 frontier 里挑 1–5 个影响最大的，写成一整轮问题，每题带建议答案
5. 等用户回答（或默认值生效）→ 把这些决策标记为已定
6. 回到 2
```

**「前置已定」自检三问**：这个问题的答案会改变我下一步写什么吗？它依赖的决策都有答案了吗？
仓库/配置/运行时能回答它吗（能 → 它是事实，自己查）？三问有一否，就还不是前沿。

**为什么一轮问整条前沿**：一轮一问会把对话拖成十几次往返，用户疲惫、积分也烧。
一轮问整条前沿 = 每轮信息量最大，且不会问到"依赖未定答案"的问题上。

## 一轮的写法

```
当前还有 3 个未定决策，一起问：

❓ Q1 — 部署目标：这版要上生产还是只在你本机跑？
➡️ 我的建议：只在本机跑，因为你说"先验证一下"。（默认：本机）

❓ Q2 — 数据来源：用现有 CSV 还是接 API？
➡️ 我的建议：先用现有 CSV 跑通链路，API 接缝留出来。（默认：CSV）

❓ Q3 — 失败处理：拉取失败要重试还是直接报错退出？
➡️ 我的建议：重试 2 次后报错退出，避免掩盖上游挂掉。（默认：重试2次）

你可以回「默认」一次全收，也可以只改第几条。
```

**紧凑式**（问题多、或回复行数预算紧时，一题一行）：

```
Q1 部署目标 — 建议：本机（默认）；理由：你说"先验证一下"
Q2 数据来源 — 建议：先用现有 CSV（默认）；理由：先把链路跑通，API 留接缝
```

两种格式别混用：≤3 题用 ❓/➡️ 两行版本，≥4 题用紧凑式，省行数也省阅读成本。

## 五维问题库（按需挑，不要全部照抄）

### Harness Engineering（怎么验证）
1. 构建 / 测试 / lint / 运行 的入口命令是什么？在哪个文件里定义？
2. 有没有 CI？CI 跑哪些步骤？（这是最权威的验收口径）
3. 本地跑需要什么环境（容器、数据库、环境变量、密钥）？现在有吗？
4. 失败的判定标准是什么？（测试红、退出码、日志关键字、UI 表现）
5. 有没有"不可在本地验证"的部分（线上依赖、第三方回调）？怎么替代验证？

### Graph Engineering（先后与并行）
1. 这批交付物里，哪个是其他东西的前置？
2. 哪些可以并行、哪些必须串行？
3. 有没有"改一处会牵动另一处"的耦合？
4. 最小可发布切片是什么？（能先端到端跑通一条最细的线吗）
5. 如果只有一半时间，优先保哪几个节点？

### Prompt Engineering（规格与验收）
1. 这次交付的验收标准逐条写出来是什么？（要能判真假）
2. 输出形态：改代码、给文档、给报告、还是给命令清单？
3. 有哪些明确禁止的做法（不许动 X 文件、不许改接口、不许加依赖）？
4. 风格/格式上有没有硬要求（命名、目录、提交信息、语言）？
5. 做到什么程度算够？什么算超范围？

### Context Engineering（信息源与边界）
1. 哪几个文件/目录是权威信息源，必须读？
2. 哪些是历史遗留、可以忽略？
3. 有没有已有的同类实现可以照抄（这是最省积分的路径）？
4. 领域术语里有没有容易理解错的黑话？
5. 文档、注释、代码不一致时，以哪个为准？

### Loop Engineering（预算与刹车）
1. 这个任务的时间/积分预算大概是多少？
2. 失败几次应该停下来找你，而不是继续试？
3. 需要中途汇报吗？多久一次？
4. 有没有"绝不能动"的底线（数据、凭据、生产环境）？
5. 做完后要留什么（提交、文档、备份）？

## 事实 vs 决策

| 问题形态 | 谁来解决 | 例子 |
|---|---|---|
| "X 现在是怎么实现的？" | 自己查（读代码/配置/git log） | "现在鉴权走哪个中间件？" |
| "X 应该怎么实现？" | 问用户 | "鉴权用 session 还是 JWT？" |
| "X 在哪定义？" | 自己查 | "这个常量在哪？" |
| "X 这个名字行不行？" | 能按现有约定推就自己定，定不了再问 | 新模块叫什么 |

判断口诀：**能 grep 出来的不许问；要承担后果的才问。** 中间还有第三类，见下。

## 三分类：事实 / 可逆假设 / 决策

| 类别 | 判据 | 处理 |
|---|---|---|
| 事实 | 能查：代码、配置、CI、运行时行为 | 自己查，**绝不问** |
| 可逆假设 | 改起来 <5 分钟、不动对外契约、不动数据、失败可回退 | 自己定，记进「已定决策」标 `(可逆)` |
| 决策 | 担后果、不可逆、改对外契约、动数据/生产 | 才占用提问名额 |

只有"决策"才该出现在问题列表里。把"新模块叫什么""日志用中文还是英文"这类**可逆假设**拿去问用户，
是在浪费用户注意力，也是在浪费积分——直接定，写进记录，错了再改的成本远低于一问一答。

## 用户说"不知道"怎么办

不要接受"不知道"当终点，给台阶：
- 给 2–3 个选项 + 每个选项的代价（"选 A 快但以后要迁移；选 B 慢但一次到位"）。
- 给推荐 + 一句理由，让用户只需点头。
- 用户仍不选 → 用推荐值开工，并把假设写进收尾尾巴。

## 何时结束 / 谁来放行

**优先放行信号**（从高到低，命中任一即可开工）：
1. 用户明确说「别问了 / 直接做 / 就按你的判断来」→ 立即开工。
2. 用户回「默认 / 都行 / 1」→ 按默认开工。
3. 无人在场（子 agent、自动化、批处理）→ 按默认开工，假设写进「已定决策」。
4. 用户在场但没回 → 给完问题与默认值后：可逆、低风险 → 按默认开工；不可逆、动数据/生产 → 停等。

注意④的边界：这里的"快与慢"比"等与不等"更贵。宁可按默认开工并明确标注假设，
也不要空转十轮等一句"嗯"。但涉及删除数据、改生产配置、对外发布时，必须第④类停等。

结束还要满足：**前沿为空**（没有"什么都没定"的分支），且输出一段合成：
已定决策清单 + 显式排除项 + "要我现在开始吗？"

## 常见坑

1. **顺序错**：问了一个依赖未定答案的问题 —— 那叫猜，不叫问。
2. **把代码能答的问题丢给用户** —— 用户会认为你没读代码。
3. **一口气甩 12 个问题** —— 超过 5 个就该砍，只留影响最大的。
4. **没有问题硬凑问题** —— 任务已经清楚就直接开工，并说明"无需追问"。
5. **接受"随便/都行"** —— 那就是默认值生效的信号，立刻定下来继续。
6. **追问期间偷偷写代码** —— 先对齐再动手；否则追问白问。
