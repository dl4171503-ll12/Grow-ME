# 自动测试轮次（grow-me 规则七详解）

> 用户说「你可以自动化测试几轮」时读本文件。核心：**把自己产出的结果提交给自己，再换两顶帽子去挑刺**，
> 每轮的发现与修复都落盘，最后给一张汇总表。

## 为什么是"提交给自己"

单轮自测的通病是"我感觉没问题"——没有对立面、没有留痕、也没有第二次机会。
拆成 **提交 → 自审 → 自试 → 择优修复 → 再提交** 之后：

- 每轮的"提交物 + 验收命令 + 发现 + 修复"变成可回看的证据链；
- 换帽子强制你做一次真正的对抗（reviewer 挑刺、新手照文档走），而不是复述自己的设计；
- 轮次文件就是跨会话的交接材料，上下文丢了也不怕。

## 何时触发 / 何时不触发

| 触发 | 不触发 |
|---|---|
| 「自动化测试几轮」「自动测几轮」「自己迭代到能用」 | 普通任务（走规则六收尾即可） |
| 「不用每轮问我」「跑完再告诉我」 | 一次性问答、发布/删除等不可逆动作（要先确认） |
| 「你提交给自己试试」 | 用户明确要求每步都确认 |

用户说了触发词 = **同时放行**：不必再问"要不要继续"，直接开始轮次；但仍受红线与预算约束。

## 单轮五步

### 第 1 步：产出
实现或修改 + 列出本轮验收命令。命令必须真能跑（见规则四 Harness）。

### 第 2 步：提交给自己
写 `.grow-me/rounds/<slug>-r<N>.md`（模板见下）。**这一步不许省**——没有提交物就没有"提交"。
提交时把"本轮要审的 3–5 个问题"先写下来，防止审的时候只挑自己擅长的那几项。

### 第 3 步：自审（reviewer 帽子）
逐条跑验收命令，只认输出。三类攻击面：

1. **边界**：空输入 / 超大输入 / 特殊字符 / 重复项 / 顺序依赖 / 编码（Windows 尤其注意 CRLF、GBK 默认编码）。
2. **失败路径**：缺参数、文件不存在、权限不足、网络断、非法值——报错信息能不能让人知道下一步做什么？
3. **证据审计**：所有"已完成""已修复""跑通了"的说法，是否都有对应的命令输出？没有就降级为"未验证"。

审的时候可以一句话自问：**"如果我是审查者，我会拿哪一条打回？"** 先写下想打回的点，再验证。

### 第 4 步：自试（第一次用角色的帽子）
假装第一次接触：只按文档/用法说明走一遍最小场景（不看实现细节）。
记录：哪一步卡住、哪句说明看不懂、哪个默认值反直觉。

### 第 5 步：修复择优
每个问题至少写 2 个修法，按三轴打分（1–5 分）：

| 维度 | 5 分 | 1 分 |
|---|---|---|
| 影响面（越小越高） | 只动一处、不动契约 | 动多处、改接口 |
| 可验证性（越强越高） | 一条命令就能证明好了 | 只能"看着像好了" |
| 回滚成本（越低越高） | 一行 revert | 要迁移/清数据 |

选总分最高的那个，把"候选 A/B + 选择 + 理由"写进轮次文件。**不做"两个都试"**——那是积分黑洞。

## 轮次文件模板

```markdown
# r<N>/<R> — <任务> — <日期时间>
状态：通过 | 有未修问题 | 阻塞 | 中断（用户插话）

## 提交物
- 产物：<路径>（diff 摘要：新增 X 行 / 改 Y 个文件）
- 验收命令：`<command>`

## 本轮要审的问题
1. <问题>
2. <问题>

## 自审发现
| 级别 | 发现 | 证据 | 修法候选 | 选择 |
|---|---|---|---|---|
| P0 | <一句话> | `<命令>` 输出：<关键行> | A/B | A（理由：影响面最小且可被测试证明） |

## 自试发现
- 按文档第 N 步卡住：<原因>
- 错误提示无法行动：<原文> → 建议改成 <文案>

## 本轮结论
- 通过（0 未修）→ 收尾
- 或：仍有 2 个问题 → 下一轮只修这两个
```

## 停止条件

| 条件 | 动作 |
|---|---|
| 本轮 0 个未修问题 | 提前停，直接收尾 |
| 达到 N 轮（默认 3，最多 5） | 停，汇总并标注"剩余问题" |
| 同一条 bug 连修 2 轮仍红 | 停手，给两个最佳方案 + 推荐，交用户拍板 |
| **用户发来新消息** | **立刻停**：当前轮落盘 + ≤8 行汇报（优先于上面一切） |
| 单轮预算耗尽（≤10 调用 / ≤2 重试） | 停该轮，记录卡点，按"2 轮仍红"处理 |

## 最终汇总表

```markdown
| 轮次 | 发现 | 修复 | 状态 |
|---|---|---|---|
| r1 | 3（P0×1, P1×2） | 3 | 通过 |
| r2 | 0 | - | 干净收尾 |
```

## 反模式

1. **假轮次**：每轮只改措辞/注释，不修实体问题。判定：轮次文件里"修复"列全是文字变化。
2. **不落盘**：只在回复里说"我又查了一遍"，没有 round 文件。
3. **无限循环**：没有 N 上限，或"零问题"了还继续跑。
4. **跳过自试**：只跑自己的测试，从不照文档用一遍。
5. **自审变自夸**：写"检查通过，无问题"，没有命令证据。
6. **用户插话不停**：用户已经给了新指令，还在"让我把这轮跑完"。

## 和用户插话的交互

用户在你跑到 r2 中途发来新消息 → 立即：

1. 把当前轮的文件补完（提交物、已发现的问题、已做的修复）；
2. 记录状态 `r2：中断（用户新指令）`；
3. 回复 ≤8 行：跑到第几轮 / 已发现什么 / 已修什么 / 当前是否可用 / 建议下一步；
4. 不再继续 r3，除非用户在新指令里说继续。
